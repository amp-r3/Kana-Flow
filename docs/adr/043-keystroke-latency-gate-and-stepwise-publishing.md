# ADR 043: Keystroke Latency Gate and Stepwise Stream Publishing

- **Status:** In force. Refines [ADR 040](040-text-stream-window-and-dom-writer.md) (when the stream changes).
- **Context:** The spec ([Quality](../spec/quality.md)) requires a keystroke p95 of at most 8 ms of work and at most 2 frames to the next paint at 4× CPU throttling. The first measurement failed: 9.2 ms of work. The cause was not the keystroke itself but the DOM mutation and layout on every completed prompt, because `stream` changed each time the caret moved to the next prompt.
- **Decision:**
  - **Stepwise publishing.** `stream` is replaced only when `shouldPublish` says so: fewer than `MIN_AHEAD_TOKENS` (44) tokens are left ahead of the caret, or more than `MAX_BEHIND_TOKENS` (60) are behind it. The matcher still holds up to `AHEAD_TOKENS` (72) and keeps `BEHIND_TOKENS` (30) after a redraw. Most prompt completions change no DOM.
  - **Probe in a test build only.** `lib/latency-probe.ts` records, per accepted keystroke, the work (entry of the handler to the end of a forced layout in a microtask) and the time to the next frame, and exposes them as `window.__nekotypeProbe`. It exists only when the build constant `__LATENCY_PROBE__` is true (`pnpm run build:probe` into `dist-probe`). `check-budget.mjs` fails when a production `dist` contains the marker.
  - **Playwright `latency` project.** It serves `dist-probe` with `vite preview` (the dev server is not representative), throttles the CPU 4× through CDP, types 200 keys (every 25th wrong) in 3 runs and compares the median of the three p95 values with the budgets. It is part of `verify` and CI. The e2e suite runs on its own port (5273) and never reuses a running server.
- **Justification:** Moving the redraw off most completions removes the dominant cost without touching the hot path. The probe measures what a user feels (layout included) and costs nothing in production.
- **Consequences:** At 4× throttling: work p95 1.9–2.3 ms, frame p95 23–25 ms. Frame time is the tighter budget (33.3 ms), so a noisy CI runner would fail there first; if it does, find the cause and decide together, do not loosen the budget. The render-isolation test accounts for the stepwise redraw.
