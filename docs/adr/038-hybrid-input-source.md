# ADR 038: Hybrid Input Source

- **Status:** In force; amended by [ADR 051](051-input-source-rules.md) (composition, held keys, Ctrl/Cmd+Enter). The open Gboard question below is still open: the device check was deferred to P7 ([Phases](../spec/phases.md)). Supersedes the `event.code` fallback of the baseline (D15) and [ADR 013](013-trailing-extension-absorption-and-desktop-input-normalization-features.md) for input.
- **Context:** Input came from `keydown` only. A mobile keyboard reports `Unidentified` there, so a phone could not type; a Cyrillic layout was translated silently by the physical key (`event.code`); and the Japanese IME notice appeared on any composition, including the Latin composition of Gboard. The spec ([Frontend](../spec/frontend.md), D14, D15) asks for a hybrid source and a layout notice.
- **Decision:**
  - **Three paths into one intent stream.** `keydown` with a Latin letter, `-` or `'` is handled at once and cancelled (desktop). `beforeinput` of type `insertText` is handled and cancelled when it is cancelable (iOS, most mobile keyboards). When it is not (Gboard composition), `input` compares the field with the last value seen and processes only what was added at its end. Anything else (a replacement, a deletion, a paste) is not typing.
  - **The field.** The hidden input is uncontrolled. It is not cleared during a composition and is cleared when one ends and after every input outside one. Composition text is recognised by its input type as well as by the composition events, so an event out of order cannot clear the field mid-word and type the word again.
  - **Layouts.** `event.code` is no longer used. A letter outside the Latin alphabet is cancelled, is not a mistake and does not start the test; the notice "Switch your keyboard layout to English" shows until the next Latin character. A key with a modifier is never intercepted.
  - **IME.** The notice "Turn off the Japanese IME" shows when composition data (or typed text) holds kana or kanji, and not for Latin composition. It hides when a Latin character is typed directly; Latin composition text does not hide it, because an IME that is on starts each word with Latin letters.
  - **Where it lives.** `features/training/lib/input-source.ts` owns the listeners and the two notices; the session no longer knows about composition. `TestStage` binds it in a layout effect, so a key pressed at once is not lost. `handleIntent` stays as the seam for an on-screen keyboard.
  - **Focus.** A typable key pressed outside the field returns the focus to it and is processed; Esc outside only returns the focus. Another text field and an open dialog are left alone.
  - **Tests.** Pure classification and the source are unit-tested with synthetic event sequences (desktop, mobile, Gboard, a Japanese IME). Chromium e2e drive the DevTools IME (`Input.imeSetComposition`), whose events match Gboard's (a `beforeinput` that cannot be cancelled), including ten prompts typed by composition with no mistake. WebKit runs the suite in iPhone emulation. Real Gboard and iOS Safari remain a manual check (`quality.md`, device matrix).
- **Justification:** Reading the field instead of the keys is the only way to see what a mobile keyboard types, and the diff rule gives the same characters whatever the composition does to the rest of the word. Translating by the physical key hides a wrong layout and mis-scores users of layouts where Latin letters sit on different keys; asking is honest and costs one key. Alternatives rejected: always reading `input` (a slower path for the desktop, which has exact keys); clearing the field on every input (breaks a composition); one notice for both problems (the fixes differ: the layout or the IME).
- **Open:** a trailing duplicate after a commit on some Gboard versions would type a word twice. The Chromium emulation does not show it; the Android check decides whether a guard is needed.
