# ADR 055: The Input Field Lives on the Page; Hover, Tab and Enter on the Test Screen

- **Status:** In force. Amends [ADR 041](041-test-screen-cutover.md) on the hidden interface and where the field lives.
- **Context:** Review of the test screen found five gaps. (1) Restart has `opacity: 0` and shows only on focus, so a mouse user cannot find it, though it can be clicked. (2) On a phone the field was part of the test screen, so Restart, Finish and "Next test" unmounted it or took the focus away; the new field was focused in an effect, outside the gesture, and the keyboard could close. (3) The rows dialog could be opened over a running test, which then ran on behind it (even to its end, with the results under the dialog). (4) Tab pressed while the interface was shown hid it again, so the navigation could not be reached by keyboard; the starting point of a mouse movement was reset only by a movement, so a slow drift over a whole test showed the interface. (5) Enter on the results screen worked only with the focus on the button; after a click beside it, it did nothing.
- **Decision:**
  - **Hover.** On a device with hover, Restart is also shown while the mouse is over it.
  - **The field is the page's.** `TrainerPage` renders the hidden field and calls `useTestInput(session, active)`; it stays in the document on both screens. Restart, the zen Finish button and "Next test" call `focusInput()` synchronously in their click handler, before the state changes. The input source is bound while the test screen shows and unbound on the results screen, so a key there is not taken from the controls. `useFinishButton` moves with the Finish button into the test screen.
  - **The dialog.** Opening the rows dialog restarts a running test (`ModePanel`'s `onOpenRows`). An idle test is left alone.
  - **The interface.** `useTestChrome` ignores Tab and Shift when it hides the interface, and every key press clears the starting point of the mouse movement.
  - **Enter.** `useEnterForNext` handles Enter on the document of the results screen unless a modifier is held, the key repeats, a dialog is open, or the focus is on a link, a control or a text field.
- **Justification:** Moving the field up is the only way to focus it inside the gesture: a component that is mounted by the state change the click causes cannot do it. The alternative, a second always-mounted field, would double the input paths. A restart on opening the dialog follows the rule that anything that takes the user away from the test discards it.
- **Consequences:** The field and the focus listener are no longer part of `TestStage`, which receives them as a prop. The results screen has no input source, so typing there does nothing. Whether the keyboard stays open on Android and iOS can be seen only on a device; the emulation checks the focus, not the keyboard.
