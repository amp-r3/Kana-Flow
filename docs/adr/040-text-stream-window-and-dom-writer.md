# ADR 040: Text Stream Window and DOM Writer

- **Status:** In force. Refines the "Window" item of [Input engine rules](../spec/engine.md) and the loading of [ADR 036](036-session-factory-and-trainer.md).
- **Context:** The text stream shows two or three lines of prompts, the line just typed above the current one. The session held the displayed prompt and two more, enough for the context of a final ん but not for the lines ahead, and `compact()` renumbers the matcher's tokens, so a view that held token numbers would need rebasing at a prompt completion. The spec asked the UI to do that rebase within the render of the completion. The hot path allows no render on a keystroke and at most one on a completion.
- **Decision:**
  - **Matcher window.** After the displayed prompt the matcher holds 60 tokens (`AHEAD_TOKENS`), filled when the displayed prompt changes, in batches sized by the average tokens per prompt seen, up to the end of a count test and never more than 150 prompts. The spec's minimum, one prompt beyond the active one, still holds. Prompts are asked for ahead of time, so a weighted source sees statistics that are at most a few dozen prompts old.
  - **Stream window.** The view draws a separate list, `stream`, of prompts with their tokens (glyph, needs no input). It keeps the data of a prompt after the matcher dropped it, and drops a prompt when it ended more than 30 tokens (`BEHIND_TOKENS`) before the caret, so the typed line stays on screen. It is a new value only when a prompt enters or leaves, which happens when the displayed prompt changes: one render per completed prompt, none otherwise.
  - **Absolute numbers.** Prompts and tokens are numbered from the start of the test. The session keeps the matcher's offset (`tokenBase`, raised by `droppedTokens`), so `compact()` changes nothing a view holds. This replaces the rebase the spec described.
  - **Per-keystroke state** is signals written in one batch: `caret` (the token the caret stands before, `view().displayedTokens`: the live conversion, which already passes tokens that need no input and may step back), `romajiBuffer` (`pendingLatin`) and `mistake` (the latest wrong key or hint: its token, a sequence number so two on one token differ, and the kind). `erroredTokens()` gives the errors of the drawn tokens, to paint a stream afresh after a render; entries leave it with the prompts.
  - **DOM writer** (`lib/stream-dom.ts`, with the arithmetic in `lib/stream-layout.ts`). A view renders the tokens once per prompt and hands over the elements. A keystroke then writes classes of the tokens whose state changed, a `translate3d` for the caret and the buffer, and a flash through `opacity`, and reads no layout: positions are measured after a render (`sync`), on a resize, when the fonts arrive, and on request. The line with the caret is kept second from the bottom; after a render the scroll is worked out again, since tokens at the top may have gone. An error stays on its token whether or not the caret has passed it.
  - This change builds the model and the writer and leaves them unused: the screen still shows one prompt. The next change replaces it.
- **Justification:** A window in tokens follows what the screen holds. Keeping the drawn prompts in the matcher means the tokens the stream draws are the ones being matched, with no second tokenisation. Numbering from the start of the test removes the rebase and the way it could be wrong. One signal per token would be a hundred and thirty subscriptions renewed at every completion; a few signals plus a writer that knows the DOM cost the same few writes per key. Alternatives rejected: a display queue outside the matcher (its tokens would be tokenised twice and could disagree with the matcher at a ん); rendering the stream from `typedBuffer` signals (a render per key); keeping the window at two prompts and drawing only the current one (the lines ahead are the point of the design).
- **Consequences:** `nextPrompt` is called about 60 times when a test loads; with a large pool (P4) the pool and its weights should be cached between calls. Performance is measured against the budgets in P2's last change.
